## 1. 基本信息与需求分析

### 需求

- [ ] REQ-1：通过稳定的 OpenCode Server/API 发现多个内部会话，并保留稳定原生会话 ID。
- [ ] REQ-2：读取每个会话的独立状态、最近活动和 OpenCode 实际提供的 Todo/规划，不推测缺失信息。
- [ ] REQ-3：按原生会话 ID 精确打开或恢复目标会话；只能激活窗口时标记为有限支持。
- [ ] REQ-4：形成可复用的 Session Adapter 契约夹具，为后续 Codex、Claude Code 接入提供同一验收面。

### 验收标准

- AC-1：同时存在至少三个 OpenCode 内部会话时，列表中的身份、项目和状态互不串扰。
- AC-2：同一会话重复扫描保持相同稳定身份，重复事件不生成重复会话。
- AC-3：打开任一会话时携带目标原生会话 ID，并通过人工观察确认进入正确会话。
- AC-4：数据源不支持的规划、事件或恢复能力明确降级，不返回伪造成功结果。
- AC-5：真实验证记录包含 OpenCode 版本、启动方式、端点、会话数量、原生 ID、状态映射和恢复结果。

### 待决策问题

- [ ] OpenCode 当前版本是否提供稳定且可重复启动的 Server/API，以及认证方式是什么。
- [ ] 精确恢复应使用 Server/API、CLI 参数还是原生深度链接；不接受仅激活应用窗口。
- [ ] OpenCode 完成、等待输入和失败状态能否通过事件获取；如果只能轮询快照，首版接入等级应标记为部分接入。

## 2. 当前实现与差距

当前 `SessionHub` 已通过 `SessionAdapter` 聚合会话，公共 Interface 只有 `list_sessions`、`probe` 和 `open_session`，适合作为第一个真实接入 seam。但运行时仍全部使用 `MockSessionAdapter`，状态、Todo、原生 ID 和恢复目标都是 Demo 数据。

主要差距：

- 没有 OpenCode 原生客户端或 HTTP 传输实现。
- 没有真实响应到 `AgentSession`、`SessionStatus`、`PlanItem` 的映射规则。
- 没有跨 Adapter 共用的多会话身份、降级行为和精确恢复契约测试。
- 没有真实 OpenCode 证据，不能声明完整或部分接入等级。
- 本机存在 OpenCode CLI，但版本探测当前出现配置目录错误，必须先验证可用启动方式。

## 3. 目标方案与对比

### 技术方案

先建立只读能力探测，确认稳定 Server/API 的会话列表、单会话详情、Todo、状态和恢复入口。探测通过后，实现 `OpenCodeSessionAdapter`，内部使用注入的 `httpx.AsyncClient` 隔离 HTTP；测试使用 `httpx.MockTransport`，生产使用真实本机端点。Adapter 只映射 OpenCode 明确返回的事实，缺失字段降级为空值或未知状态。

### 关键决策

- **先验证再接入：** Server/API 或精确恢复不稳定时停止实现，只保存验证结果，避免为不可靠入口建立生产 Adapter。
- **不使用进程/窗口作为会话事实：** 进程与窗口仅用于诊断，不能生成核心会话或证明恢复成功。
- **保持 SessionAdapter 小 Interface：** 首个纵向切片优先复用现有三个方法；只有真实 OpenCode 能提供增量事件且第二个 Adapter 也需要时，再扩展公共事件 Interface。
- **真实与测试传输分离：** HTTP Client 是 Adapter 内部 seam，不暴露给 SessionHub。

### 流程对比

```text
当前流程：Demo Seed -> MockSessionAdapter -> SessionHub -> API/UI
目标流程：OpenCode Server/API -> OpenCodeSessionAdapter -> SessionHub -> API/UI -> 精确恢复原生会话
失败流程：能力探测失败 -> 明确部分/有限支持 -> 保存验证缺口 -> 不伪装完整接入
```
