# AgentHub V1 产品需求

## 1. 产品定位

AgentHub 是面向 Windows、macOS、Linux 主流桌面操作系统的本地 AI Agent 管理中枢。它统一管理多个 Agent 的内部会话和本地能力，包括 Skill、MCP Server 与 Agent 插件。

产品解决两个核心问题：

1. 用户同时运行多个 Agent 时，集中发现需要介入的内部会话，并精确回到原生会话。
2. 用户在多个 Agent 之间复用能力时，集中查看真实安装状态，并以安全、可审计、可恢复的方式共享和管理能力。

## 2. V1 边界

### 2.1 包含

- 本地单用户、单个 AgentHub 应用。
- Codex、Claude Code、OpenCode 及后续 Agent Adapter。
- 内部会话发现、统一状态、待处理识别、规划展示和精确打开。
- Skill、MCP Server、Agent 插件的发现、共享、启用、停用、健康检查、冲突处理、审计和恢复。
- Windows、macOS、Linux 平台适配。

### 2.2 不包含

- 在 AgentHub 中直接回复会话、批准权限或执行 Agent 工作。
- 云端同步、团队权限、组织策略分发。
- 静默自动更新或未经确认的破坏性清理。
- VS Code 通用扩展、浏览器插件和其他非 Agent 插件。

会话域负责观察、提醒和精确打开；能力域负责查看和安全管理；实际 Agent 工作继续在原生客户端中完成。

## 3. 单应用要求

- 最终只发布和运行一个 AgentHub 应用。
- SkillBridge 不作为独立产品继续发展，其扫描、共享、安全、审计和回滚能力应合并为 AgentHub 的 Skill 子系统。
- 会话、Skill、MCP、插件共用 Agent 配置、能力清单、审计、数据库和管理界面。
- 子系统保留独立领域边界，不把所有生命周期压缩为一个通用开关。

## 4. Agent 与会话管理

### 4.1 Agent 配置

- 识别 Agent 类型、Agent 安装和 Agent 配置。
- 允许用户配置和验证 Agent 接入，并查看最近连接状态及失败原因。
- 独立展示会话接入等级，以及 Skill、MCP、插件各项能力的支持状态。

### 4.2 内部会话

- 发现同一 Agent 中的多个独立会话。
- 每个会话至少保留 Agent、稳定的原生会话标识、标题、项目或工作目录、统一状态、最近活动、更新时间、状态来源和精确打开入口。
- 首页核心统计围绕会话总数、执行中、等待授权、等待输入、等待验收、执行中断和已关闭展开；工具、进程和窗口数量只作为诊断信息。
- 将原生事件映射为执行中、等待授权、等待输入、等待验收、执行中断、已关闭和状态未知。
- “是否待处理”是独立于运行状态的关注维度，等待授权、等待输入、等待验收、执行中断和需要关注的状态异常都应进入待处理汇总。
- 系统应自动识别待处理状态，不提供人工标记或人工清除入口。
- 等待授权、等待输入和执行中断应在 Agent 后续事件表明会话恢复后自动解除；等待验收只有在用户继续发送指令、会话明确关闭或 Agent 上报接受结果时才能解除，仅打开会话不能视为完成验收。
- 规划展示只读取 Agent 已提供的目标、步骤、Todo 和最近结果；Agent 未提供规划时不得推测进度或生成虚假百分比。
- 打开会话必须精确恢复目标会话，不能只打开 Agent 首页或窗口。
- AgentHub 不提供会话消息输入和权限批准入口。

### 4.3 会话接入等级

- 完整接入：能够发现多个内部会话、保留稳定原生标识、独立识别状态，并精确恢复指定会话。
- 部分接入：缺少规划、事件或部分状态信息，但仍能确定会话身份并精确恢复。
- 有限接入：只能检测进程、窗口或 Agent 是否运行，不能可靠识别和恢复内部会话。
- 有限接入的数据不得纳入核心会话统计，也不得展示为已经接入内部会话。
- 一种 Agent 接入只有通过真实的多会话独立状态和精确恢复验证后，才能声明完整接入。

## 5. Skill、MCP、插件的公共规则

本章不是一个独立的“能力管理”功能模块，而是 Skill、MCP Server 和 Agent 插件共同遵循的领域模型、共享机制和状态定义。三种类型各自特有的需求分别在第 6—8 章说明。

### 5.1 公共领域模型

- 能力类型包括 Skill、MCP Server 和 Agent 插件。
- 区分能力、能力来源和能力安装。
- 同一能力可以在多个 Agent 中引用同一个真实来源。
- 名称相同但来源、Manifest 标识或内容指纹不同的能力不得自动合并。
- 每个安装独立记录 Agent、兼容性、状态、来源、健康和原生加载结果。

### 5.2 公共目录共享机制

- 对具有目录来源的 Skill、MCP 和 Agent 插件提供同源共享能力。
- Windows 优先使用 NTFS Junction；macOS 和 Linux 使用 Symbolic Link。平台差异由文件链接适配器处理。
- 启用共享时，在目标 Agent 的能力目录创建指向统一来源的目录链接，不复制内容。
- 目标位置存在真实目录时不得直接覆盖，应提示冲突并在用户确认后先备份。
- 停用共享时只删除已验证的链接，不删除能力来源。
- 目录链接建立后，Agent Adapter 仍须完成必要的原生注册、配置或刷新，并验证 Agent 已经加载该能力。
- 不支持目录发现的 Agent 或能力类型不得伪装为支持链接共享，应降级为原生配置模式或标记不支持。

### 5.3 公共安装状态

- 来源
- 共享安装
- 本地副本
- 缺失
- 冲突
- 断链
- 无效
- 未兼容
- 已分发但未原生加载
- 健康检查失败

### 5.4 卸载安装、删除来源与永久清除

- “卸载能力安装”只移除某个 Agent 中的链接、原生注册或本地安装，不删除能力来源，也不影响其他 Agent。
- “删除能力来源”属于全局完全删除操作。来源删除后，所有引用该来源的 Skill、MCP 或插件共享安装都将失效或被移除。
- 用户从来源所在位置发起卸载时，系统必须将操作识别为“删除能力来源”，不能按照普通安装卸载处理。
- 删除前必须展示能力名称、类型、来源位置、所有引用安装、受影响 Agent、插件引用关系和可能丢失的用户修改。
- 删除来源必须经过单独的明确确认；普通的卸载确认、批量选择或取消共享确认不能复用为来源删除确认。
- 用户未确认时不得修改来源、链接、原生配置或数据库记录。
- 确认后，系统先执行完整预检，再按可恢复顺序移除原生注册和共享链接，最后删除来源；任一前置步骤无法安全完成时，不得删除来源。
- 删除来源在产品语义上属于完全删除：活动来源和所有依赖安装都不再可用。为防误操作，可以在隔离备份区保留恢复副本，但不得继续把备份识别为已安装能力。
- 删除恢复备份是独立的“永久清除”操作，需要再次确认。永久清除后 AgentHub 不承诺恢复内容。
- 删除来源和永久清除都必须记录影响清单、确认结果、执行步骤、失败信息和最终状态。

## 6. Skill 专属需求

- 解析 Skill 描述、兼容性和内容指纹。
- 提供 Skill × Agent 状态矩阵。
- 支持来源选择、目录共享、批量操作、冲突处理、备份和回滚。
- 一个 Skill 被多个插件引用时，卸载其中一个插件不得删除该 Skill。
- 插件独占的 Skill 即使被用户修改，也随插件卸载；执行前必须明确提示并保留可恢复备份。

## 7. MCP Server 专属需求

### 7.1 第一阶段：只读与验证

- 发现独立 MCP 和插件携带的 MCP。
- 展示身份、来源、传输方式、启动命令或端点、配置位置、启用状态及暴露的 Tools、Resources、Prompts。
- 检查命令、目录、连接、协议和原生加载状态。
- 默认只展示敏感变量名称和是否已配置，不读取或保存明文值。

### 7.2 第二阶段：安全变更

- 支持目录共享，以及 Agent 原生配置的新增、修改、启用、停用和删除。
- 应用配置前验证，保留旧版本并支持回滚。
- 插件携带的 MCP 配置由该插件独占；卸载插件时可以随插件移除，但仍需审计和可恢复备份。

## 8. Agent 插件专属需求

- 插件仅指 Agent 原生插件机制识别的插件。
- 发现已安装和可安装插件，展示版本、来源、Manifest、兼容性、状态、更新和内含能力。
- 支持目录来源在多个 Agent 之间链接共享，并通过 Agent Adapter 验证原生加载。
- 支持安装、启用、停用、更新和卸载，所有操作产生审计记录。
- 卸载插件时移除插件独占的 Skill 和 MCP；被其他插件引用的 Skill 必须保留。
- 插件独占 Skill 即使被用户修改，也允许随插件卸载，但必须在确认界面展示修改事实并建立恢复备份。
- 插件更新与用户修改发生冲突时不得自动覆盖，应展示差异和影响，由用户选择保留修改、采用更新或取消。

## 9. 安全、审计与恢复

- 仅监听本机地址。
- 所有路径操作必须规范化并限制在已配置能力目录、来源目录或备份目录中。
- 秘密不得出现在 UI、日志、数据库、导出和诊断中。
- 修改操作记录操作者、对象、前后状态、步骤、结果、错误和备份位置。
- 支持自动回滚、补偿恢复、人工恢复和不可逆四种恢复等级，并在执行前展示。
- 文件系统、Agent 原生 API 和配置是事实来源，数据库保存配置、快照和审计。

## 10. 跨平台要求

- 支持 Windows 10/11、主流 macOS 和主流桌面 Linux 发行版。
- 平台文件系统操作必须通过统一适配接口实现。
- Windows 覆盖 Junction、ReparsePoint、路径盘符和占用错误；macOS/Linux 覆盖 Symbolic Link、权限和大小写差异。
- BDD 与 Adapter 契约测试在三个平台使用等价场景；平台专属行为由对应集成测试补充。
- 某个平台未通过真实验证时必须标记为实验性支持，不得仅凭代码路径存在声明完整支持。

## 11. 完整支持标准

一种能力类型只有满足以下条件才能标记为完整支持：

1. 至少两个 Agent 通过真实发现。
2. 能准确区分来源、安装、冲突和加载状态。
3. 启用和停用行为确定且可重复。
4. 失败不会损坏真实来源，并有可验证的恢复路径。
5. Adapter 契约测试和平台集成测试通过。
