下面整理为三部分：**需求总结、技术方案、原型微调说明**。内容以当前讨论结论为准，重点突出“内部会话聚合”，不再把普通进程和窗口管理作为核心价值。

# AI Agent 会话聚合管理台

## 需求与技术方案总结 V0.2

## 一、项目定位

开发一个运行在 Windows 本地的轻量级 AI Agent 会话聚合管理台，用于统一查看 Codex、Claude Code、OpenCode 等 Agent 工具中的内部会话，并快速进入指定会话继续处理。

产品核心价值不是管理应用窗口，而是：

```text
看见所有 Agent 内部会话
        ↓
识别每个会话当前状态
        ↓
发现需要人工介入的会话
        ↓
一键进入指定会话继续处理
```

如果某个工具只能识别应用进程或窗口，无法识别内部会话，也无法精确恢复指定会话，则只能作为有限支持工具，不属于产品核心能力。

---

# 二、核心需求

## 2.1 多 Agent 工具接入

首期重点考虑：

* Codex
* Claude Code
* OpenCode

后续根据实际可行性增加：

* Gemini CLI
* Cursor
* Windsurf
* 其他桌面或 CLI Agent

不同 Agent 的会话机制、状态接口和恢复方式不同，需要分别实现适配器，不能只依靠通用进程扫描。

---

## 2.2 内部会话聚合

系统需要读取各 Agent 工具内部的真实会话，而不是只统计进程或窗口数量。

例如：

```text
Codex
├── Nacos 监听方案
├── Kafka 压测
└── Agent Hub 原型开发

Claude Code
├── Skill 文档整理
└── 数据架构设计
```

每个会话至少展示：

* Agent 工具名称；
* 会话名称或主题；
* Agent 原生会话 ID；
* 所属项目或工作目录；
* 当前状态；
* 当前规划或步骤；
* 最近执行内容；
* 最后更新时间；
* 是否需要人工处理；
* 精确恢复入口。

---

## 2.3 会话数量统计

首页需要展示：

* 会话总数；
* 正在执行数量；
* 等待授权数量；
* 等待输入数量；
* 等待验收数量；
* 异常中断数量；
* 已关闭数量。

工具数量、进程数量和窗口数量可以作为辅助信息，但不作为首页核心指标。

---

## 2.4 统一会话状态

不同 Agent 的原始状态需要映射成统一状态。

建议使用以下状态：

| 状态   | 含义                     | 是否待处理 |
| ---- | ---------------------- | ----: |
| 执行中  | Agent 正在调用模型、工具或执行命令   |     否 |
| 等待授权 | 等待用户确认权限或执行操作          |     是 |
| 等待输入 | Agent 主动提出问题，等待用户回答    |     是 |
| 等待验收 | 当前轮次或规划已经执行结束，需要用户检查结果 |     是 |
| 已中断  | 执行失败、进程异常退出或会话异常       |     是 |
| 已关闭  | 会话已正常归档、结束或关闭          |     否 |
| 状态未知 | 无法从当前适配器判断准确状态         | 视情况提示 |

不再使用“空闲”状态，因为它含义模糊，且难以准确判断。

---

## 2.5 待处理逻辑

“待处理”不是与“正在运行”互斥的状态，而是一个关注维度。

例如：

| 会话情况       | 是否运行 | 是否待处理 |
| ---------- | ---: | ----: |
| Agent 正常执行 |    是 |     否 |
| 等待权限授权     |    是 |     是 |
| 等待用户回答     |    是 |     是 |
| 执行完成，等待验收  |  可能是 |     是 |
| 任务异常中断     |  可能否 |     是 |
| 已正常关闭      |    否 |     否 |

待处理内容主要包括：

```text
等待授权
等待用户输入
等待验收
任务中断
状态异常
```

待处理状态应由 Agent 事件、会话数据或日志自动识别，不提供人工“标记待处理”功能。

---

## 2.6 待处理自动解除

待处理状态应根据 Agent 后续事件自动解除。

### 等待授权

```text
Agent 发出权限请求
        ↓
进入待处理
        ↓
用户完成授权
        ↓
Agent 恢复执行
        ↓
自动解除待处理
```

### 等待输入

```text
Agent 提出问题
        ↓
进入待处理
        ↓
用户发送新消息
        ↓
Agent 恢复执行
        ↓
自动解除待处理
```

### 任务中断

```text
执行失败或会话异常退出
        ↓
进入待处理
        ↓
会话重新恢复并继续执行
        ↓
自动解除中断状态
```

### 等待验收

等待验收的自动解除比较特殊。

只有检测到以下事件时，才能可靠解除：

* 用户继续向该会话发送新指令；
* 会话被明确归档或关闭；
* Agent 提供“接受结果”“完成”或类似事件；
* 客户端插件明确上报验收完成。

仅仅点击“打开会话”不能代表已经验收完成。

---

## 2.7 会话规划展示

系统应尽量读取 Agent 内部已有规划，不自行生成任务计划。

展示内容可以包括：

* 当前目标；
* 规划步骤数量；
* 已完成步骤；
* 当前步骤；
* 待执行步骤；
* Todo 列表；
* 最近一次执行结果。

示例：

```text
当前目标：完成 Kafka 疲劳压测脚本

规划进度：4 / 6

✓ 分析现有脚本
✓ 调整消息生成逻辑
✓ 增加多 Topic 支持
✓ 完成均匀发送测试
● 验证间歇发送
○ 输出压测结果
```

如果某个 Agent 不提供规划或 Todo 信息，则只展示可获得的会话状态和最近活动，不虚构百分比进度。

---

## 2.8 精确进入指定会话

每个会话卡片都需要提供：

```text
打开该会话
```

该操作应优先使用 Agent 原生会话恢复能力，而不是简单激活应用窗口。

优先顺序：

```text
Agent 官方会话 API
        ↓
Agent CLI Resume 命令
        ↓
Agent 插件或深度链接
        ↓
定位原终端或桌面窗口
        ↓
只能打开工具首页
```

只有能够根据会话 ID进入准确会话，才视为完整支持。

# 三、技术方案

## 3.1 总体架构

```text
浏览器管理页面
        ↓
Python FastAPI 本地聚合服务
        ↓
统一会话管理与状态转换
        ↓
不同 Agent 适配器
        ↓
Agent API / Hook / 会话文件 / CLI
```

系统建议继续使用：

```text
后端：Python + FastAPI
数据：SQLite
前端：HTML + JavaScript，后续可升级 Vue
实时更新：SSE 或 WebSocket
部署：start.bat，后续可使用 PyInstaller
```

Python主要负责会话数据聚合、状态转换、事件接收和调用 Agent 恢复命令。

Windows 进程和窗口探测仅作为辅助能力。

---

## 3.2 Agent 适配器架构

每种 Agent 实现独立适配器。

统一接口建议包括：

```text
list_sessions()
get_session(session_id)
get_session_status(session_id)
get_session_plan(session_id)
get_session_events(session_id)
resume_session(session_id)
close_session(session_id)
get_capabilities()
```

适配器返回统一数据结构，由管理台负责展示。

示例：

```text
OpenCodeAdapter
CodexAdapter
ClaudeCodeAdapter
CursorAdapter
```

---

## 3.3 统一会话数据模型

建议的会话结构：

```text
Session
├── id                    管理台内部 ID
├── native_session_id     Agent 原生会话 ID
├── tool_id               Agent 工具
├── title                 会话名称
├── project_name          项目名称
├── working_directory     工作目录
├── runtime_status        运行状态
├── execution_status      执行状态
├── attention_required    是否待处理
├── attention_reason      待处理原因
├── current_goal          当前目标
├── current_step          当前步骤
├── plan_items            规划步骤
├── last_activity         最近活动
├── last_updated_at       最后更新时间
├── resume_method         恢复方式
├── status_source         状态来源
└── confidence            状态可信度
```

建议保留“状态来源”和“可信度”。

例如：

```text
状态来源：Agent Hook
可信度：高
```

或者：

```text
状态来源：终端输出推断
可信度：中
```

避免将推测状态展示成确定事实。

---

## 3.4 OpenCode 接入方案

OpenCode优先通过本地 Server API 接入。

主要能力：

* 获取全部会话；
* 获取会话详情；
* 获取会话状态；
* 获取 Todo 或规划；
* 获取会话变更；
* 订阅事件流；
* 恢复或打开指定会话。

适配流程：

```text
调用 OpenCode Server
        ↓
读取 Session 列表
        ↓
读取 Session 状态和 Todo
        ↓
转换为统一状态
        ↓
通过 Session ID 打开指定会话
```

OpenCode可以作为首个完整适配对象。

---

## 3.5 Codex 接入方案

Codex优先通过 App Server、Thread 或 Hook 机制接入。

主要需要验证：

* 是否能够获取全部 Thread；
* 是否存在稳定 Thread ID；
* 是否能够读取当前状态；
* 是否能够读取 Goal 或规划；
* 是否能够监听权限请求；
* 是否能够监听当前轮次完成；
* 是否能够恢复指定 Thread。

状态映射示例：

```text
Permission Request
        → 等待授权

Thread 正在执行
        → 执行中

当前轮次正常停止
        → 等待验收

执行错误
        → 已中断
```

点击打开时，根据 Thread ID恢复指定会话。

---

## 3.6 Claude Code 接入方案

Claude Code优先通过 Hooks 和 Session ID 接入。

需要采集：

* session_id；
* cwd；
  -用户输入事件；
  -权限请求事件；
  -任务创建与完成事件；
  -正常停止事件；
  -失败停止事件。

状态映射示例：

```text
PermissionRequest
        → 等待授权

Agent 提问并停止
        → 等待输入

Stop
        → 等待验收

StopFailure
        → 已中断

新的 UserPromptSubmit
        → 解除待处理并进入执行中
```

点击打开会话时调用：

```text
claude --resume <session-id>
```

恢复指定会话。

---

## 3.7 桌面客户端接入原则

Cursor、Windsurf 等桌面客户端需要单独验证。

只有满足以下至少一项，才进行完整接入：

* 提供会话 API；
* 提供插件或扩展机制；
* 提供可读取的本地会话数据库；
* 提供稳定的 Session ID；
* 提供深度链接；
* 能够通过插件打开指定内部会话。

如果只能识别：

* 应用是否运行；
* 有几个窗口；
* 当前窗口标题；

则只能标记为有限支持。

有限支持工具只提供：

```text
打开客户端
激活窗口
展示已知项目
```

但不纳入核心会话统计，避免造成“已支持内部会话”的误解。

---

## 3.8 辅助进程探测

`psutil` 和 `pywin32` 仍然保留，但作用降级为：

* 判断 Agent 服务是否启动；
* 判断对应会话进程是否异常退出；
* 获取终端或桌面窗口；
* 在原生恢复失败时尝试激活窗口；
* 辅助识别项目目录；
* 辅助记录运行时间。

不能仅凭进程状态判断任务完成、等待授权或等待验收。

---

# 四、实施阶段

## 4.1 第一阶段：技术可行性验证

先不继续扩展页面功能，优先验证三个 Agent。

### OpenCode

验证：

* 列出多个内部会话；
* 获取每个会话状态；
* 获取规划或 Todo；
* 识别待处理；
* 打开指定会话。

### Codex

验证：

* 获取多个 Thread；
* 获取稳定 Thread ID；
* 获取规划或状态；
* 识别权限请求和正常结束；
* 恢复指定 Thread。

### Claude Code

验证：

* Hook 上报多个 Session；
* 识别权限、停止和失败；
* 获取 cwd 和 Session ID；
* 使用 Session ID恢复指定会话。

技术验证标准：

```text
同一工具同时存在三个内部会话
        ↓
管理台准确显示三个会话
        ↓
每个会话状态独立
        ↓
任意点击一个会话
        ↓
准确恢复到对应会话
```

至少两个核心 Agent 通过验证后，再进入正式开发。

# 六、最终范围结论

产品核心范围确定为：

```text
跨 Agent 内部会话发现
        ↓
会话规划和状态聚合
        ↓
待处理事项自动识别
        ↓
精确进入指定会话
```

以下能力降级为辅助能力：

```text
进程探测
窗口探测
应用启动
窗口激活
项目文件夹打开
```

以下能力暂不实现：

* 完整任务管理；
* 任务看板；
* 多 Agent 自动分配；
* Agent 自动协作；
* Git、PR、CI 管理；
* 管理台内直接输入和授权；
* 复杂桌面 UI 自动化。

项目是否值得继续开发，取决于能否对至少两个主要 Agent 实现：

```text
准确发现内部会话
准确识别会话状态
读取基本规划信息
精确恢复指定会话
```

原型下一步只需进行上述页面文案和数据字段微调，不建议继续增加窗口、进程类功能。
