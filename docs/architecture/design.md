# AgentHub V1 技术设计

## 1. 文档目的

本文描述 AgentHub V1 当前统一技术方案，连接 PRD、ADR、BDD 和后续代码实现。它是可更新的设计文档；已经落地的实际结构以 `overview.md` 为准，关键且难以逆转的选择单独记录在 `adr/`。

## 2. 设计目标

- 最终只运行一个 AgentHub 应用。
- 聚合 Codex、Claude Code、OpenCode 等 Agent 的内部会话。
- 统一管理 Skill、MCP Server 和 Agent 插件。
- 支持 Windows、macOS、Linux 主流桌面系统。
- 文件系统和 Agent 原生 API/配置是事实来源。
- 目录链接只代表内容分发，Agent 原生加载必须独立验证。
- 所有破坏性操作可审计、可预检，并具有明确恢复等级。

## 3. 总体结构

```text
浏览器 UI
  -> FastAPI API
  -> 应用服务
       ├── 会话服务
       ├── 能力清单服务
       ├── 共享与生命周期服务
       └── 审计与恢复服务
  -> 领域模型与 Repository
  -> Adapter
       ├── Agent Adapter
       ├── 能力类型 Adapter
       └── 平台链接 Adapter
  -> Agent API / Hook / 配置 / CLI / 本地文件系统
```

UI 只使用归一化读取模型，不解析 Agent 原生配置，也不直接执行系统命令。

## 4. 领域模型

### 4.1 Agent

- `AgentType`：Codex、Claude Code、OpenCode 等产品类型。
- `AgentInstallation`：当前系统中的一份 Agent 安装。
- `AgentProfile`：AgentHub 保存的接入配置。
- `AgentSession`：具有稳定原生标识、可独立查看状态和恢复的内部会话。

### 4.2 能力

- `Capability`：逻辑上的 Skill、MCP Server 或 Agent 插件。
- `CapabilitySource`：能力内容的唯一真实来源。
- `CapabilityInstallation`：能力在某个 Agent 中的可发现安装。
- `SharedInstallation`：通过目录链接引用来源的安装。
- `PluginOwnership`：插件与其独占 Skill、MCP 配置之间的生命周期关系。

同名能力不能仅凭名称合并，应结合能力类型、Manifest 标识、来源和内容指纹识别。

## 5. 会话设计

1. Agent Adapter 发现内部会话和原生事件。
2. 会话服务将原生状态映射为执行中、等待授权、等待输入、等待验收、执行中断、已关闭或状态未知。
3. 待处理状态由统一状态自动推导，并根据后续原生事件解除。
4. 用户点击打开时，服务根据原生会话标识调用精确恢复能力。
5. AgentHub 不直接回复会话或批准权限，用户回到原生 Agent 完成操作。

事件驱动用于实时更新，周期扫描用于最终一致性，手动刷新作为兜底。

## 6. 能力发现与状态

1. 加载启用的 Agent Profile。
2. Agent Adapter 给出 Skill、MCP、插件的原生发现位置和注册方式。
3. 能力扫描器识别真实目录、目录链接、Manifest、内容指纹、配置和加载状态。
4. 清单服务将实例按能力身份聚合，并推断来源和插件所有权。
5. 读取模型生成 Skill/MCP/插件 × Agent 状态矩阵。

公共状态包括来源、共享安装、本地副本、缺失、冲突、断链、无效、未兼容、已分发但未原生加载和健康检查失败。

## 7. 跨平台目录共享

平台链接 Adapter 提供创建链接、解析目标、验证链接、移除链接和检测断链的统一契约：

- Windows：NTFS Junction。
- macOS/Linux：Symbolic Link。

共享流程：

1. 校验来源、目标和允许操作的根目录。
2. 检查目标是否缺失、真实目录、正确链接、错误链接或断链。
3. 目标为真实目录时暂停操作，展示冲突并要求确认备份。
4. 建立平台目录链接。
5. Agent Adapter 执行必要的原生注册、配置或刷新。
6. 验证 Agent 已经加载能力；否则标记为“已分发但未原生加载”。

## 8. 卸载与删除来源

### 8.1 卸载能力安装

只移除一个 Agent 的链接、原生注册或本地安装，不影响能力来源和其他 Agent。

### 8.2 删除能力来源

这是全局破坏性操作：

1. 分析全部共享安装、Agent、插件引用和用户修改。
2. 展示完整影响并要求独立确认。
3. 对全部依赖执行可撤销预检。
4. 安全取消原生注册和目录链接。
5. 删除活动来源，并将恢复副本移入隔离备份区。
6. 记录每一步和最终状态。

任一前置依赖无法安全处理时，不得删除来源。永久清除隔离备份需要再次确认。

## 9. 插件生命周期

- 插件可以包含 Skill、MCP、App 和其他 Agent 扩展。
- 被多个插件引用的 Skill 不随单个插件卸载。
- 插件独占 Skill 即使被用户修改，也可以在提示和备份后随插件卸载。
- 插件携带的独占 MCP 配置可以随插件卸载。
- 更新与用户修改冲突时停止自动更新，展示影响并由用户选择。

## 10. MCP 设计

第一阶段只读发现和验证：统一身份、传输方式、命令或端点、配置位置、Tools、Resources、Prompts 和健康状态。

第二阶段开放安全变更：新增、修改、启用、停用、删除、版本备份和回滚。敏感值不写入 UI、日志、数据库或导出；默认只展示变量名称和是否配置。

目录型 MCP 可以通过链接共享内容，但 Agent 原生配置仍由 Adapter 管理。

## 11. 持久化与事实来源

SQLite 保存：

- Agent Profile
- 会话快照和状态事件
- 能力身份、来源选择和扫描快照
- 插件所有权和依赖关系
- 操作审计、备份位置和恢复状态

数据库不决定文件或 Agent 的真实状态。服务启动、手动刷新和操作完成后都应重新扫描事实来源并校准缓存。

## 12. 安全与恢复

- 服务仅监听本机地址。
- 所有路径先规范化并验证位于允许根目录中。
- 不对磁盘根目录、用户主目录或 Agent 能力根目录本身执行递归删除。
- 所有修改操作记录前后状态、步骤、错误和备份。
- 恢复等级分为自动回滚、补偿恢复、人工恢复和不可逆。
- 破坏性操作必须在执行前展示影响范围和恢复等级。

## 13. API 与 UI 边界

API 按会话、Agent、能力清单、Skill、MCP、插件、操作审计划分资源。UI 提供统一导航和状态矩阵，但三种能力的详情与操作流程保持原生语义。

会话页面提供查看、筛选、待处理汇总和精确打开；不提供直接聊天或授权。能力页面提供发现、共享、原生加载验证、冲突处理和安全生命周期操作。

## 14. 验证要求

- BDD 验证用户可观察的业务行为。
- 单元测试验证解析、状态映射、路径和冲突规则。
- Adapter 契约测试验证各 Agent 的发现与生命周期接口。
- 平台集成测试分别验证 Junction 和 Symbolic Link。
- 破坏性操作只在已确认的临时夹具中测试。
- 一种能力至少在两个 Agent 中通过真实发现和确定性启停后，才标记为完整支持。

## 15. 待细化事项

- 中央能力来源目录的默认位置和迁移策略。
- 首批真实 Agent Adapter 的实现顺序。
- 各 Agent 的 MCP 和插件原生注册差异。
- 插件可安装来源及版本信任规则。
- SQLite 表结构和并发操作锁。
- 桌面打包、托盘和自动启动方案。
